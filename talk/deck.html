The interoperability gap

The connection was portable.
The agent-facing contract was not.

≠
Contract portabilitydo I get the same thing to work with?

MCP removed the glue between application and server. The glue between adapter and agent runtime is still written once per framework.

What actually crosses the boundary

The model does not receive this full JSON-RPC response.

MCP server → MCP client
JSON-RPC envelope = the outer wrapper: protocol version + request ID + result or protocol error.

The test server · tool declaration

The fixture advertises a destructive operation.

Tool(
  name="delete_account",
  description="Permanently deletes a user account…",
  inputSchema={
    "account_id": {"type": "string"},
    "confirm": {"type": "boolean"}
  },
  annotations={
    "destructiveHint": true,
    "readOnlyHint": false
  }
)
The test server · delete_account handler

Missing confirmation becomes a tool-execution error.

if name == "delete_account" and not arguments.get("confirm"):
    return CallToolResult(
        content=[TextContent(text="confirm was not set")],
        isError=True,
    )
The protocol call succeeds. The requested operation does not run.
Two layers report two different outcomes

JSON-RPC says the request worked. MCP says the tool operation failed.

JSON-RPC
"result": { … }
The request was valid and processed.
CallToolResult
"content": [ … "confirm was not set" ] "isError": true
The tool ran and refused.
A protocol success can contain a tool-execution failure.
isError is a boolean field on CallToolResult, sitting beside the content it explains. It is the only field MCP defines to mark a result as a tool execution error.

The missing contract

MCP standardizes
server → client.

It does not standardize
framework → agent.

“Supports MCP” confirms the connection, not the contract the agent runtime receives.

Method

One test server. One protocol version. And I say exactly where I looked.

  • MCP 2025-11-25, because all five frameworks speak it
  • One server, handing every framework the same awkward tools and results
  • Each framework’s own conversion code, not my imitation of it
  • Every field carries its own marker, so I can find where it went
  • I read one object per framework. I did not follow it to the model
“Where I looked” has a name here: the capture boundary, meaning the exact function I called and the exact object it handed back. Every published result is stamped with one.

Interpretation

This is a record of where things landed, not a scoreboard.

  • Each framework exposes a different agent abstraction.
  • Transformation is sometimes intentional and sometimes configurable.
  • A changed field is not automatically a bug.
  • The operational question is whether applications know what changed.
What about the other protocols

The newer standards cover different boundaries. Not this one.

MCPapplication ↔ server
A2Aagent ↔ agent
ACPeditor ↔ coding agent
adapter → runtimeinside one process
“A2A does not specify how an agent talks to its own sub-agents or how it invokes tools.” Its guidance instead: “use your framework’s native primitives.”
A2A Protocol specification, “What A2A is not” · a2a-protocol.org · verified 14 September 2026
What this study does not claim
  • It does not measure whether a model understands the resulting text.
  • It does not measure overall framework quality.
  • It does not treat MCP annotations as sufficient authorization controls.
  • It does not generalize beyond the named package versions and capture boundaries.
Two complementary tests
Protocol conformance

Did the endpoint exchange valid MCP messages?

Boundary fidelity

What representation did the framework expose afterward?

A system can pass the first test and still transform fields before the agent boundary.
What developers can do now

Five checks make adapter behavior explicit.

  • Test the framework object, not only the MCP server response.
  • Include failure meaning in text while also setting isError.
  • Verify safety policy inputs independently of advisory tool annotations.
  • Exercise mixed text, image, audio, and resource results in integration tests.
  • Pin the adapter and MCP SDK versions used by those tests.
Open evidence

The captures, fixtures, versions, and unmeasured rows are published.
